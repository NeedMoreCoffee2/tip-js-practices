## 3. Реализация

### 3.1. HTTP-клиент

Метод requestJson был расширен для поддержки методов GET, POST, PATCH и DELETE. Если передается body, он автоматически сериализуется через JSON.stringify, а в заголовки добавляется Content-Type: application/json. Для GET передача тела запрещена. Ответ 204 No Content обрабатывается возвратом null до попытки чтения JSON. Тайм-аут (AbortSignal.timeout) и внешний AbortSignal объединяются.

### 3.2. Доменный API

В task-api.js реализованы операции: getTasks, getTaskById, getCategories, createTask, updateTask, setTaskCompleted, deleteTask, resetDemoData. Схема ответа проверяется до передачи данных в контроллер (функции isTask и isCategory). Если сервер возвращает неверный формат или deleteTask не возвращает null, выбрасывается ApiError с kind: "invalid-response".

### 3.3. Состояния интерфейса

Переходы состояний осуществляются через view.setListState():

- loading — устанавливается перед каждым сетевым запросом.

- ready — отрисовка карточек и количества задач при успешном непустом ответе.

- empty — показывается сообщение «По выбранным условиям задач нет», если ответ успешен, но массив пуст.

- error — выводится текст ошибки и кнопка повтора.

При повторной загрузке старые карточки полностью заменяются с помощью replaceChildren.

### 3.4. Изменение данных

Создание, редактирование и удаление обернуты в общую функцию performMutation. Перед изменением кнопки блокируются (чтобы избежать двойной отправки). После успешного ответа сервера форма очищается, а затем выполняется повторный запрос GET (через loadCurrentTasks). Это гарантирует, что интерфейс отображает актуальное состояние сервера с учетом текущих фильтров.

### 3.5. Защита от устаревшего ответа

Для предотвращения гонки запросов (когда старый запрос завершается позже нового и перетирает данные) используется AbortController — при каждом новом запросе предыдущий отменяется. Дополнительно контроллер хранит счетчик loadSequence, и результат запроса применяется только в том случае, если его номер совпадает с последним запущенным. Ошибки с kind: "aborted" не показываются пользователю.

## 4. Индивидуальный вариант

**Начальный фильтр:** _completed=true_<br>
**Индивидуальный сценарий:** _Завершить видимую задачу. После повторного GET она должна исчезнуть из выборки._

- Входные данные: Применен фильтр completed: true (отображаются только выполненные задачи).

- Действие: Нажата кнопка "Вернуть в работу" (смена статуса completed на false) у одной из задач.

- Ожидаемый результат: Запрос PATCH успешно меняет статус на сервере. Последующий GET возвращает список только с completed: true, поэтому измененная задача исчезает из отображения.

- Фактический результат: Задача исчезла из списка, счетчик общего количества задач уменьшился на 1. Состояние интерфейса соответствует ожиданию.

## 6. Ответы на контрольные вопросы

1. _Почему `fetch` не отклоняет Promise при ответе 404?_
  fetch отклоняет Promise только при сетевых сбоях (когда ответ от сервера вообще не получен, например, нет соединения). Статус 404 означает, что сервер доступен и успешно отправил HTTP-ответ, просто с кодом ошибки. Поэтому fetch разрешает Promise с объектом Response, где response.ok равно false. Ошибку нужно проверять вручную.
2. _Почему ответ 204 нельзя разбирать вызовом `response.json()`?_
   Статус 204 No Content означает, что запрос выполнен успешно, но тело ответа отсутствует. Вызов response.json() попытается прочитать пустую строку как JSON, что вызовет SyntaxError. Поэтому перед парсингом нужно проверять статус и возвращать null.
3. _Чем состояние `empty` отличается от `error`?_
   empty — это нормальное состояние, когда запрос выполнен успешно (статус 200), но сервер вернул пустой массив (например, из-за фильтров). error — это сбой (сетевая ошибка, тайм-аут или 5xx), когда данные получить не удалось. В состоянии error пользователю предлагается кнопка повтора, в empty — нет.
4. _Зачем отменять предыдущий запрос при смене фильтров?_
   Если пользователь быстро меняет фильтры, запросы уходят один за другим. Из-за разницы в скорости сети старый (ненужный) запрос может завершиться позже нового и перезаписать актуальные данные в интерфейсе. Отмена через AbortController экономит ресурсы и предотвращает гонку данных.
5. _Почему после мутации список повторно запрашивается у API?_
   Сервер является единственным источником истины. После создания, изменения или удаления задачи локальная копия данных в браузере устаревает. Повторный GET-запрос с текущими фильтрами гарантирует, что интерфейс покажет именно то, что реально сохранено на сервере.
